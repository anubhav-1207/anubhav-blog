What happens inside an interpreter?

A tree-walking interpreter in four stages — and why the seams between those stages are the interesting part.

2026-11-18 interpreters 6 min read

Most explanations of interpreters describe them as a loop: read a statement, do the statement, repeat. That is true the same way that "a compiler turns source into machine code" is true — accurate, and useless the moment something goes wrong.

The clearer picture is a pipeline of four stages, each of which hands the next stage a value it can no longer take back. Once you see those four handoffs, most interpreter bugs announce themselves as "which stage produced this wrong thing?" rather than "the language is broken".

Try this. Draw the four boxes on paper. When something misbehaves, point at the first box whose output already looks wrong. That is where the bug is.

Four stages, one contract

Source text goes in at the left. At each step, the representation becomes more structured and loses more of the original document:

  • Lexing — characters become tokens. Whitespace and comments are gone.
  • Parsing — tokens become a tree. Parentheses are gone; precedence is baked into the shape.
  • Resolution — names become references. Scope becomes explicit.
  • Evaluation — the tree becomes values. Everything after this is behaviour, not structure.

Each stage is a pure function of its input, or close enough. That is the whole trick: if the lexer is correct, the parser can assume a clean stream of tokens, and no later stage ever has to think about a stray comment.

1. The lexer discards what it does not need

A lexer is small enough to hold in your head. Its job is to collapse runs of characters into a single labelled token, and to stop caring about everything else:

// one token at a time; no context, no backtracking
func (l *Lexer) next() Token {
    l.skipSpace()
    if l.atEnd() {
        return Token{Kind: EOF}
    }

    ch := l.peek()
    switch {
    case isDigit(ch):
        return l.number()
    case isLetter(ch):
        return l.identifier()
    default:
        return l.punct()
    }
}

Notice how little the lexer knows. It does not know that if starts a statement, or that + binds tighter than ==. It sees a character and emits a token. Keeping it ignorant is what makes it easy to test: feed it a string, compare the token list.

The one place lexers get complicated is when a token depends on context — string interpolation, nested block comments, Python's significant indentation. That complexity is real, and it is usually the first sign that the language is asking the lexer to do the parser's job.

2. The parser builds the thing everyone depends on

The parser's output is the contract for the rest of the program. In a tree-walking interpreter, that contract is a small set of node types:

type Expr interface { exprNode() }

type Binary struct {
    Op    Token
    Left  Expr
    Right Expr
}

That is the entire idea of an abstract syntax tree: 1 + 2 * 3 and 1+(2*3) produce the same tree, because the tree records structure and nothing else. Precedence stops being a parsing detail and becomes a property of the data.1

Because the AST is the contract, it is also the first thing to freeze when you are learning. Add nodes when you need them; change their shape rarely. Every pass you write later — a resolver, a type checker, an evaluator — is written against this tree, and each one is a small recursive function over it.

A parser that only ever produces correct trees is a parser with no error messages.

3. Evaluation is the smallest piece

In a tree-walker, the evaluator is embarrassingly direct: eval switches on the node type, recurses into children, returns a value. For the whole expression language above it is perhaps forty lines. The interpreter is not the evaluator; it is the lexer, the parser, and the environment that the evaluator threads through.

That environment is where the real design lives. A lexical scope is a chain of maps; a closure is a function plus the scope it was defined in; assignment is a lookup followed by a mutation. None of that is visible in the grammar, and all of it determines whether the language feels coherent.2

What this buys you

Once the stages are separate, each one becomes independently testable, and each bug has an address. Wrong token? Lexer. Wrong shape? Parser. Right shape, wrong answer? Evaluator or environment. That is a much better debugging experience than staring at a stack trace that spans all four.

It also makes the next step obvious. Swap the tree-walker for a compiler that emits bytecode, and the lexer and parser do not change at all — you replace the last stage and keep the contract. That is the point of the pipeline: the seams are meant to be cut.

  1. Tree-walking and bytecode compilation are not rivals so much as different answers to "how much structure do I keep at runtime?" A tree-walker keeps the program's shape visible, which makes error messages and debugging easier. A bytecode VM keeps it flat, which makes execution faster. ↩
  2. The other half of that design is error recovery. Stopping at the first syntax error is trivial; continuing to parse so an editor can report three errors at once is what separates a toy from a tool. ↩
